# Research: Soft parameter sharing for conflicting tasks (absolute-position vs translation-invariant + spectral auxiliary)

## Summary
Hard sharing is the wrong prior when tasks need mutually exclusive features (absolute position vs translation invariance): the trunk cannot satisfy both, so one channel collapses — exactly what you observe. The strongest evidence for resolving *destructive* interference (not just mean-accuracy gains) is for architectures that give each task a private subspace and learn the sharing from data: cross-stitch (Misra et al., CVPR 2016), sluice networks (Ruder et al., 2017), and MMoE→PLE (Ma et al., KDD 2018; Tang et al., RecSys 2020). For a 2-task small-GAT trunk, the recommended design is: duplicate the trunk into two task towers, stitch/fuse only at/after pooling with near-identity init (start from the healthy solution, diverge only as needed), and confine the routing auxiliary loss to the intrinsic branch with a one-way gate.

## Findings
1. **Cross-stitch has the most direct "destructive-interference resolved" evidence, with a usable init recipe.** Two task towers + per-layer linear-combination ("stitch") units learn how much to share; init diagonal α≈0.9 / off-diagonal ≈0.1 biases training to start near two independent networks and only share as useful. On semantic segmentation + surface normals and attribute + detection pairs, stitch nets beat both single-task and hard-shared baselines; the authors explicitly frame test cases with "little data" per category where hard sharing hurts. The learned α values are interpretable (high sharing early, task-specific late). [Paper (CMU/CVPR 2016)](https://publications.ri.cmu.edu/storage/publications/pub_files/2016/6/multi-task.pdf) [arXiv](https://arxiv.org/abs/1604.03539); init (0.9, 0.1) convention [figure note](https://www.researchgate.net/figure/Using-cross-stitch-units-to-stitch-two-AlexNet-32-networks-In-this-case-we-apply_fig1_301876767). Failure modes: full tower duplication doubles params; stitch units are dense linear mixes so with a 140k trunk × 2 this is fine, but on large backbones it is costly; stitching too early on *conflicting input encodings* (your raw-vs-centered coordinates) still mixes incompatible signals — stitch after the encoding conflict is resolved, not before.
2. **Sluice networks generalize cross-stitch and say *where* to split: learn subspaces × layers × skip connections.** Each layer's representation is split into two subspaces with learned α (which subspace of which task flows where) and β (which layer's output each task head reads). This subsumes hard sharing, cross-stitch, and task-hierarchy models as special cases; on loosely related NLP tasks sluice beats hard sharing and cross-stitch, and follow-ups confirm label-entropy predicts when sharing helps. Directly answers Q2: don't hand-pick early/late — fit α/β and read off where sharing survives; expectation for your setup is α→block-diagonal (private subspaces) in layer 1 (position vs shape separate) with possible sharing at pooled level. [arXiv 1705.08142](https://arxiv.org/abs/1705.08142v1) [overview with Fig. 8](https://arxiv.org/pdf/1706.05098). Failure modes: the paper itself notes sluice "easily fits noise" (many sharing params, needs regularization/dropout); gains are small when tasks are already closely related.
3. **MMoE→PLE is the strongest evidence at scale for *seesaw/negative-transfer* specifically, and the closest analog to an auxiliary loss hijacking the trunk.** MMoE (KDD 2018): shared experts + per-task gates; "if tasks are less related, sharing is penalized and gates learn to use different experts." PLE (RecSys 2020, 900+ cites) names your symptom — the *seesaw phenomenon* (one task improves only by hurting another) — and fixes MMoE's residual sharing by separating shared vs task-specific experts with progressive routing; it resolves negative transfer on conflicting recommender tasks where MMoE still seesawed. [MMoE KDD PDF](https://dl.acm.org/doi/pdf/10.1145/3219819.3220007) [KDD page](https://www.kdd.org/kdd2018/accepted-papers/view/modeling-task-relationships-in-multi-task-learning-with-multi-gate-mixture-of-experts) [PLE ACM](https://dl.acm.org/doi/fullHtml/10.1145/3383313.3412236). Failure modes: expert collapse / polarization (gates route everything to one expert — needs load-balancing/dropout); overkill for 2 tasks (PLE's full progressive stack matters at many tasks); still needs loss balancing alongside architecture.
4. **NDDR / cross-task attention (Gao et al., CVPR 2019) and task-attention (MTAN, CVPR 2019) are the "late-fusion" variants — useful mechanism, weaker destructive-interference evidence.** NDDR concatenates task features then 1×1-conv/BN reduces dimension per layer (426+ cites, plug-in for pretrained single-task nets); MTAN adds task attention masks + adversarial gradient alignment so no task dominates the trunk. Both preserve single-task starting points well, but neither was validated on *mutually exclusive input encodings* like yours; NDDR's 1×1 fusion assumes spatially aligned feature maps, which raw-vs-centered GAT features violate at the node level. [NDDR CVPR PDF](https://openaccess.thecvf.com/content_CVPR_2019/papers/Gao_NDDR-CNN_Layerwise_Feature_Fusing_in_Multi-Task_CNNs_by_Neural_Discriminative_CVPR_2019_paper.pdf) [code](https://github.com/ethanygao/NDDR-CNN) [MTAN arXiv](https://arxiv.org/abs/1904.08918) [MTAN code](https://github.com/facebookresearch/astmt).
5. **Auxiliary SSL on one branch under gating: yes, there is precedent, and gating changes the auxiliary from "trunk shaper" to "branch shaper" — which is what you want.** MTAN-style task masks, MMoE gates, and sluice β weights all confine auxiliary gradients to their branch by construction; gradient methods that instead keep hard sharing (PCGrad projects conflicting gradients, GradNorm/UW reweight them) treat symptoms while the representational conflict remains — PCGrad's own results are strongest in RL/multitask-CIFAR, not on encoding-incompatible tasks. [PCGrad NeurIPS 2020](https://arxiv.org/pdf/2001.06782v2) [LibMTL method survey](https://arxiv.org/pdf/2203.14338). Expectation: with a one-way gate (stop-gradient from auxiliary branch into context branch), the routing loss still shapes the intrinsic branch's geometry (test: triplet accuracy + Slepian recoverability move together on that branch) while the context branch is provably insulated (test: zone F1 stays ≥0.9 while gates learn). If gates saturate open, you have re-created hard sharing — monitor gate/α entropy as the early warning.
6. **Capacity guidance: minimum overhead ≈ 2× trunk + small fusion is the honest floor; anything less re-imposes the conflict.** Cross-stitch/MMoE-with-2-experts both need roughly two task towers; PLE needs shared + 2× specific. At ~140k params this is ~280–350k total — affordable and justified because your conflict is representational (absolute vs invariant), not just gradient-magnitude. Do not try to save capacity with a shared first GAT layer over mixed raw/centered inputs: that layer is where the collapse originates (position-destroying centering vs position-needing readout cannot co-exist in one linear map).

## Ranked designs for OUR setting (≤3)
**Design 1 (recommended): Late-stitch dual-GAT — duplicate trunk, stitch only post-pooling, routing loss confined to intrinsic tower.**
Mechanism: tower C (context: raw coords → 2-layer GAT → team-mean pool → zone/centroid heads); tower I (intrinsic: centered coords → own 2-layer GAT → pool → triplet head + Slepian routing head). Fuse only pooled vectors: [c_out; i_out] per tower = [[α_cc, α_ci],[α_ic, α_ii]] [c;i], one 2×2 α per tower (4 scalars), or a small NDDR-style linear+BN. Init α=diag(0.9)/off-diag(0.1) (cross-stitch convention) with tower weights warm-started from your healthy 20-epoch checkpoints (C from context-only run, I from intrinsic-only run); freeze towers 2–3 epochs while α warms, then unfreeze. Routing/triplet gradients flow only into tower I (stop-grad on α_ci path into C). Why it survives: no shared layer ever sees both encodings; training starts exactly at the healthy solution (identity-ish α + healthy weights) and sharing only grows if it lowers validation loss. Cost ≈ 2× trunk + heads. Key refs: Misra et al., CVPR 2016; Gao et al. (NDDR), CVPR 2019.
**Design 2 (cheapest informative): Sluice-lite — shared layer-0 stem split into private subspaces + learned β readout.**
Mechanism: keep one GAT layer-1 but split channels into [shared | context-private | intrinsic-private] thirds; learned α mixes only within compatible groups; each head reads all layers via learned β (skip). Init α block-diagonal (private=0.9, cross≤0.1), β favoring late layer. Why: tests whether *any* sharing is viable at minimal overhead (~1.2× trunk); if α stays block-diagonal, you have learned proof of irreconcilability and fall back to Design 1. Risk: layer-0 still sees both encodings — feed towers separate input projections (raw vs centered) before any mixing. Key ref: Ruder et al., arXiv 1705.08142 (2017).
**Design 3 (if 1 still seesaws): CGC/PLE-mini + PCGrad on gates only.**
Mechanism: Design-1 towers + one small shared expert beside them (CGC separation: shared vs specific experts, per-task gates); auxiliary routing loss only on intrinsic-specific expert; apply PCGrad projection solely at the gate/fusion parameters, not inside towers. Why: PLE is the only family with documented seesaw elimination after MMoE; combining architectural separation (handles your encoding conflict) with gradient surgery (handles residual loss-scale conflict) covers both failure axes. Cost ≈ 2.5× trunk. Key refs: Ma et al., KDD 2018 (MMoE); Tang et al., RecSys 2020 (PLE); Yu et al., NeurIPS 2020 (PCGrad).

## Gaps
- No published result combines a Slepian-spectral auxiliary with gated MTL on GNNs — Q3's "does the auxiliary still shape anything" must be settled empirically (proposed check: triplet accuracy vs Slepian-recoverability correlation within tower I while zone F1 is held fixed).
- No capacity-overhead theorem for 2-task GATs; "2× trunk is the floor" is an argument from the encoding conflict, not a cited bound.
- Early-vs-late evidence is from CNN/NLP backbones; GAT-specific split-point evidence is absent — recommend logging learned α/β per layer rather than trusting transferred heuristics.
